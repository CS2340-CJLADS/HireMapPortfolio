Process Description

We followed Scrum and documented design principles, patterns, and decisions. Here is a description on how we used these for each of our sprints.

Scrum

  • Two-week sprints with sprint goals
  • Daily stand-ups (15 minutes)
  • Backlog refinement & sprint planning
  • Reviews & retrospectives
  • Roles: Scrum Master, Product Owner, Devs

Design Decisions

  • Django Framework
  • Django Templates for UI
  • Modular, scalable components
  • Accessibility (contrast, keyboard nav)

General Overview

A concise summary of how we approached building the project across analysis, design, implementation principles, and continuous refinement.

  1. 1. Analysis: Defining "What" We Built

    The foundation of our project began with Requirements Engineering. We translated the project's goals into a clear, actionable backlog using the Agile way. This involved:

    • User Stories: Defining all features in the "As a [Role], I want [Feature], So that [Benefit]" format. This ensured every feature was tied to a specific user goal.
    • System Sequence Diagrams (SSDs): We created flow charts to map the interactions between our users (the Actors) and the system. This black-box view allowed us to understand the flow of events before designing the internal logic.

  2. 2. Design: Planning "How" We Built It

    With a clear analysis, we moved to Object-Oriented Design (OOD), opening the black box to plan our application's structure.

    • Software Architecture: We chose the Django framework, which follows a Model-View-Template pattern and provides a clean layered architecture separating data (Model), business logic (View), and presentation (Template).
    • Design Diagrams: We created a Design Class Diagram (DCD) to get a unified idea of how the pages will function and used Sequence Diagram concepts to model object collaborations for each user story.

  3. 3. Principles: Building It "Well"

    We emphasized maintainability by applying fundamental OOD design principles such as SOLID and GRASP.

    We learned the importance of high cohesion and low coupling: our initial per-user-story division produced tight coupling and blockers. Creating a shared Design Class Diagram enforced single responsibility and the Information Expert pattern, enabling decoupled, parallel development.

  4. 4. Refinement: Improving Our Process

    We applied refactoring not only to code (fixing code smells) but also to our team's workflows.

    • Process Refactoring: We migrated from a scattered Trello setup to a more streamlined GitHub Projects workflow.
    • Workflow Refactoring: We redesigned our GitHub branching and merging strategy to avoid merge conflicts and improve developer velocity.

    This iterative application of analysis, design, and refinement allowed us to build a more complex application and a more effective team.

Sprint 1

Sprint 1 Analysis: Process & Tools

As our team's first sprint, our initial focus was on establishing our Scrum process and tools. While we successfully set up our core platforms, our retrospective revealed significant flaws in our execution and group habits.

What Worked
  • Communication: We established a strong communication system in Microsoft Teams by creating a new, dedicated thread each week. This prevented disconnected posts, made it easy to track weekly activity, and ensured all shared files were easily searchable.
  • Backlog Management: Our Trello board was well-organized and effective for showcasing tasks and ownership.
What Didn't Work
  • Poor Source Control: Our GitHub usage produced many disconnected branches and frequent merge conflicts; this culminated in a demo issue where the wrong branch was used on a presentation laptop.
  • Weak Meeting Cadence: While Teams was effective, we failed to hold one full-team meeting outside class and attendance at Monday TA meetings was inconsistent.
The Core Challenge: A Flawed "Per-User Story" Strategy

Our initial approach — assigning each teammate a full user story end-to-end — introduced several structural problems:

  • Dependency Blockers: Not everyone was full-stack; front-end and back-end work created blocking dependencies.
  • Rift in Understanding: Parallel changes without shared design led to mismatches between front-end expectations and back-end implementations.
  • Overlapping Work: Multiple stories depended on shared subsystems (e.g., account creation), which compounded delays.
TA Feedback

Our TA, Mr. Zheng, praised our user flow but highlighted missing UI basics: a logout button and a navbar for easier navigation (the lack of which forced reliance on the browser back button).

Impact of Missing Architectural Diagrams

One critical issue was the absence of architectural or flow diagrams: without a visual shared model, the team held divergent mental models of the system, which made it difficult to coordinate implementation across layers.

The following two diagrams were created after the sprint review to communicate a shared understanding and to drive Sprint 2 planning:

Diagram 1 (above) was an early attempt at a User Experience Interaction Flow: it aimed to give everyone a simple, page-level view of the site—showing key pages, how they connected, and a brief technical note about what each page requires. Although this provided a basic shared picture, the diagram did not go far enough to resolve the misunderstandings we were experiencing and ultimately fell short of preventing integration issues.

Diagram 2 (above) was a quicker, hand-drawn iteration that dug deeper into informational flows and component interactions. This informal version improved everyone’s understanding more than the first, but it arrived late—after much of the sprint's work was already underway—so it forced additional rework to align implementations with the clarified design.

Our Action Plan: A New Strategy for Sprint 2

  • New Development Strategy: Abandon per-user-story work division; create a comprehensive list of requirements and visual artifacts, then break work up on a page-by-page basis.
  • Improved Scrum Process: Mandate at least one 30-minute full-team meeting weekly outside class and enforce Monday TA meeting attendance.
  • New GitHub Workflow: Introduce a clear branch strategy using Sprint-#-Main branches to streamline merging.
  • Role Changes: Move Ali Vafaeian to Scrum Master and to fullstack (along with James Armendariz) to address front/back imbalances.

These diagrams and the action plan were used to re-align priorities for Sprint 2 and to remove the ambiguity that had slowed Sprint 1.

Sprint 2

Sprint 2: A Successful Pivot to OOD

Our second sprint was defined by a complete pivot in strategy, directly addressing the failures of Sprint 1. We moved from a chaotic, code-first approach to a structured Object-Oriented Design (OOD) process grounded in formal diagrams and software-design principles.

What Worked: The Power of Design-First

The biggest win in this sprint was prioritizing Object-Oriented Analysis and Design before implementation. This design-first stance eliminated many previous blockers and clarified responsibilities.

  • Formal Diagramming: We created two key artifacts that guided implementation:
    • System Flow Chart (SSD): A black-box view defining the interactions between actors and the system, used to scope interfaces and user flows.
    • Design Class Diagram (DCD): A backend-focused class model and rough method list that gave the team a shared architecture and allowed backend work to proceed independently.
  • Applying OOD Principles: With a DCD we enforced Low Coupling and the Information Expert principle; backend developers could implement features against well-defined contracts, removing dependency blockers.
  • Process Refactoring: We continued refining our sprint process and reduced team-level process smells through clearer planning and documentation.
  • Source Control: We implemented a clearer GitHub branching and merging workflow (Sprint-#-Main pattern), which immediately reduced merge conflicts.
  • Tooling: We migrated from Trello to GitHub Projects and made tasks into GitHub Issues, streamlining work and tying tasks directly to the repository.
What Didn't Work: External Time Management

While the OOD approach was successful, our progress was hampered by an external time conflict: the Exam 2 alternative assignment. Mid-sprint priorities shifted, freezing active development. This highlighted the need to plan around academic deadlines.

Our Action Plan: Further Refinement
  • Earlier Planning: Complete planning and diagramming earlier in the sprint cycle to avoid late-stage surprises.
  • Intensive Work Sessions: Hold at least one extended meeting outside class to establish major requirements and make concentrated progress together.
Diagrams & Artifacts

Though not a formal diagram, we decided to list out every app and their required methods to not leave front and back end developers guessing. The related apps are accounts, recruiter, seeker, and messages, which handle the bulk of the functionality of our website. Functionally this diagram serves some of the same purposes as a DCD in that it gives everyone a clear naming scheme, and although interactions are described, we left displaying interactions to a different diagram.

The first of our diagrams, our model class diagram. This was created at the start of our project to describe the different models in our system and which ones are related to each other. Though we made a few errors with this diagram, such as inconsistent arrow directions and missing or incorrect information, it gave us a solid ground to develop the required parts of our first sprint, as well as dive deeper into what was missing and create new diagrams for our other two sprints.
